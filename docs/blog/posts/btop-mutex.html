btop's broken lock

the mutex that wasn't

25 Aug 2026 · btop · C++ atomics · PR #1649

I had been seeing btop crash every now and then. In January 2025 I opened issue #1012 with a core dump. It looked related to CPU cores being off-lined, but it was rare enough that I could not make it happen on demand. I poked around, hit some other sanitizer failures, opened #1042, then left it alone for a while.

About a year later I came back to it and started following the races again. While looking at the UI thread and runner thread, I ended up in the tiny custom atomic lock used all over the codebase. I was not really looking for a lock bug. I just opened the implementation.

WTF. The mutex was not a mutex.

There were actually two problems in the same area. The blocking lock could let more than one thread through, and Runner::active was waited on with relaxed ordering even though the rest of the code used that wait like a real thread hand-off.

Small distinction: I am not saying PR #1649 fixed the original CPU-hotplug crash in #1012. That one is still open. It is just how I ended up looking here. The races from #1042 are what this PR actually fixed.

Bug #1: compare-exchange let a second thread in

Before the fix, atomic_lock was basically a std::atomic<bool> with RAII around it. Construction set it to true, destruction put it back to false. With wait=true, the constructor used compare-exchange and was meant to wait until it could flip unlocked to locked.

Before PR #1649btop_tools.cpp
atomic_lock::atomic_lock(atomic<bool>& atom, bool wait) : atom(atom) {
    if (wait)
        while (not this->atom.compare_exchange_strong(this->not_true, true));
    else
        this->atom.store(true);

    this->atom.notify_all();
}

atomic_lock::~atomic_lock() noexcept {
    this->atom.store(false);
    this->atom.notify_all();
}

The part that looked wrong was not_true. It starts as false, then the same variable is reused as the expected argument to compare_exchange_strong every retry.

The one compare-exchange detail that matters here is this:

atom.compare_exchange_strong(expected, desired)

If atom == expected, it stores desired and returns true. If not, it returns false and writes the value it saw back into expected.

That write-back is the whole bug.

Thread A does false → true and enters. Thread B starts with expected == false, sees the atomic is already true, and the first CAS correctly fails. But that failure also changes B's expected to true.

And the loop never resets it.

So B retries with expected == true. The atomic is still true because A still owns the lock. Comparison succeeds, desired is also true, so this is just true → true. C++ says success and B leaves the loop.

Now A and B both think they own it.

So this was not some fairness problem. One failed compare-exchange could turn the next loop iteration into a successful no-op. Anything relying on atomic_lock(..., true) for actual mutual exclusion could overlap.

Where btop was using it

At the May 2026 revision I was working from, the waiting form guarded at least these two paths:

Terminal resize

term_resize() used atomic_lock lck(resizing, true) to prevent concurrent resize handling. The broken CAS meant re-entry was still possible.

Config writes

Config::write() waited on writelock and then used atomic_lock lck(writelock, true). Two writers could pass the guard at once.

This is where I had the obvious question: how did this survive for so long? Mostly because the bad timing has to actually happen. If the second thread arrives a little later, fine. If those paths almost never contend, also fine. Even if they overlap, you still need them to touch something where the overlap matters. Then some machine or timing change makes it suddenly visible.

Undefined behavior does not have to be dramatic. A broken mutex can sit there for years because most runs never hit the exact timing that proves it is broken.

Bug #2: seeing an atomic flag is not synchronization

The compare-exchange bug was pretty obvious once I slowed down and read it. The memory-ordering one was less loud.

btop has a runner thread doing collection and drawing, while the main/input thread also changes config and UI state. Runner::active was used as the gate between them. Runner marks itself active while doing unsafe-to-overlap work, and main-thread code waits on it before touching shared state.

The wait helper was this:

Old waitbtop_tools.cpp
void atomic_wait(const atomic<bool>& atom, bool old) noexcept {
    atom.wait(old, std::memory_order_relaxed);
}

void atomic_wait_for(const atomic<bool>& atom, bool old, uint64_t wait_ms) noexcept {
    while (atom.load(std::memory_order_relaxed) == old && ...)
        sleep_ms(1);
}

relaxed is fine if the only thing you care about is the atomic itself. It keeps that atomic coherent. It does not make the normal reads and writes around it magically line up with another thread.

But callers were doing more than waiting for a boolean. They treated Runner::active == false as “runner is done, shared state is safe for me now”. That needs a real synchronization edge.

For this pattern, the runner needs to publish “I am done” with release semantics, and the waiter needs acquire semantics when it observes that state. Then the ordinary work before the release is ordered before ordinary work after the acquire.

Less standardese: the flag change becomes the hand-off. Stuff runner did before unlock is visible before the UI continues after the wait.

My first fix was just to make that contract real: acquire on the waits, release on unlock/store.

Commit 88b0ed6, then tightened by 5aaca91 and 312592fview commit
void atomic_wait(const atomic<bool>& atom, bool old) noexcept {
    atom.wait(old, std::memory_order_acquire);
}

bool expected = false;
while (!atom.compare_exchange_strong(
    expected,
    true,
    std::memory_order_acquire,
    std::memory_order_relaxed
)) {
    expected = false;
}

// unlock
atom.store(false, std::memory_order_release);

The failed CAS can still be relaxed because it did not acquire the lock. The important bits are: reset expected before retrying, acquire when ownership succeeds, release when unlocking.

The race that got me here: current_preset

The thing that originally pulled me into this was Config::current_preset, a std::optional<int> touched by both input handling and drawing.

The runner read it while drawing:

!Config::current_preset.has_value()
    ? "*"
    : to_string(Config::current_preset.value())

Meanwhile p/P could change the same optional from the input thread. There was an atomic_wait(Runner::active) in the path, which looked reassuring until I noticed it happened after the reads and mutations:

Before 557fbe5btop_input.cpp
const auto old_preset = Config::current_preset;

// reads and writes current_preset here
...

atomic_wait(Runner::active);
Config::apply_preset(...);

So the wait was on the wrong side. By the time it waited for runner, the racy access had already happened.

557fbe5 moved the wait above the first access. I then found two menu paths that could also reset current_preset while runner was drawing, so 677336f put the guard there too.

This is why fixing only the lock helper was not enough. A perfect lock cannot protect an access that happens before you take it.

Why I stopped forcing timed waits through the atomic

The first version fixed the atomic semantics. A day later I changed the runner state again and made atomic_waiting_lock, backed by a normal std::mutex and std::condition_variable.

Not because atomics are bad. The API just wanted both normal waits and timed waits, and C++ atomic wait/notify is awkward for the timed part. The old atomic_wait_for basically polled the atomic and slept for 1 ms between checks.

A condition variable fit the job better:

class atomic_waiting_lock {
    bool value{};
    mutable std::mutex mtx;
    mutable std::condition_variable cv;
    ...
};

void atomic_waiting_lock::wait_for(bool old, uint64_t ms) const noexcept {
    std::unique_lock lock{mtx};
    cv.wait_for(lock, std::chrono::milliseconds(ms),
                [this, old] { return value != old; });
}

Runner::active moved from atomic<bool> to that class, and runner gets an RAII guard from active.lock(). State change, waiting, timeout, notification and lock lifetime all live in one place now.

I kept the small generic atomic_lock for simple boolean guards, with the CAS loop fixed. Runner had a more annoying contract, so it got the mutex + condition variable version instead.

A few other things from the same sweep

Once I had sanitizer builds going and was already reading nearby code, a few unrelated fixes came along with the PR too.

Teardown from the signal handler

The SIGINT handler could call clean_quit(0) directly. That function joins threads, writes config, logs, formats strings, touches the terminal, and can allocate. Basically a list of things you do not want to run from an asynchronous POSIX signal handler.

3843042 changed SIGINT to set state and call Input::interrupt(). That helper is only kill(getpid(), SIGUSR1); normal program flow wakes up and does the real shutdown later, outside the handler.

An Intel GPU failure-path leak

327f695 also fixed two early-return leaks around gpu_device_name, plus the engine structure when PMU init failed. Nothing to do with the lock really; same sanitizer run found it.

This lock had already changed once before

I checked the history because I wanted to know where this lock came from. In October 2021 btop replaced atomic-bool spinlocks with mutexes in 804fe60, specifically for a rare deadlock. Three days later 1601422 moved back to custom atomic-bool locks. The compare-exchange version that was still there in 2026 comes from around that time, with wait/notify added later.

I am not saying using atomics there was stupid. There can be decent reasons: hot paths, portability at the time, library support, wanting a tiny primitive. But once you build something mutex-shaped yourself, you also own all the boring mutex guarantees. One owner. Correct wakeups. Correct publication. Correct lifetime. And memory ordering that still works somewhere other than your own x86 machine.

Atomics are tiny code with a lot of contract attached to them.

So why did it work for years?

Because “has a race” and “crashes every run” are very different things.

  • The compare-exchange bug only shows itself when threads actually contend on a wait=true path.
  • The relaxed-ordering bug needs ordinary shared accesses to overlap while code is relying on that atomic transition as the hand-off.
  • CPU count, terminal activity, I/O, optimization, sanitizers, kernel scheduling... all of these move the timing window around.
  • x86 is also fairly forgiving. Bad C++ ordering can look fine there for a long time; the language-level race is still undefined behavior.
  • And even if two threads enter together, you still need the overlap to hit state where somebody notices.

This is why TSan helped a lot here. It does not need the race to become a visible crash first. It points at conflicting accesses without a valid happens-before relation. That got me close enough; reading the synchronization code did the rest.

The open-source part of this

btop is mature, widely used software. This lock was still wrong for years. Both can be true.

I do not think the interesting question is “how did the maintainers miss this?” A project like btop has more platforms, hardware combinations and weird runtime paths than a small maintainer group can continuously stare at. This kind of thing is normal.

If you use it and have time, there are a lot of useful ways to help. Reproduce one annoying crash. Run a sanitizer build. Review a change. Fix something small. Or sponsor the project if that is easier.

I started from a crash I could barely reproduce. A year later I followed a few sanitizer reports, then one synchronization path, then another, and eventually found a lock that could let two threads own it. Bit of a detour, but a useful one.
